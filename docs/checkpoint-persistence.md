# Checkpoint persistence diagnosis and fix

## Confirmed root cause

The original section-progress transaction inserted the lesson successfully, then ran this module-summary expression with untyped parameters:

```sql
CASE WHEN $1 = $2 AND $2 > 0 THEN 'completed' ELSE 'started' END
```

PostgreSQL inferred the compared parameters as text before reaching the integer comparison. Executing the exact original statement in an isolated schema reproduced SQLSTATE **42883**, `operator does not exist: text > integer`. The failed statement aborted the transaction, rolling back the lesson insert. A generic API 500 then produced the frontend's unhelpful checkpoint banner. This is a reproduced SQL failure, not an inference from a browser error alone.

The fixed statement casts counts to `integer` explicitly in both assignments and comparisons. The existing PostgreSQL connection, verified TLS, authentication, CORS, session cookies and CSRF architecture are unchanged.

## Transaction and state changes

- [progressService](../backend/src/progressService.js) validates stable lesson IDs, checks out the existing pool's client inside the error boundary, and locks the authenticated user's row before changing progress.
- Lesson state, module counts and activity history are saved in one transaction. Activity failure can no longer produce an error after progress was already committed. A rollback failure cannot hide the original error.
- Duplicate completion is idempotent: it preserves completion timestamps and does not add duplicate activity. Automatic starts carry `startedOnly: true` so stale requests cannot reopen completed lessons. Explicit checklist unchecking still works.
- A single PostgreSQL statement returns the user-scoped progress snapshot. PATCH returns that snapshot only after commit. GET and PATCH responses are `private, no-store`.
- Once reading progress exists, mastery changes cannot overwrite its module count. Historical completed module records remain respected unless a reading lesson is explicitly reopened.
- [progressStore](../frontend/src/services/progressStore.js) updates shared state after server confirmation, guards duplicate writes, rejects stale account responses, deduplicates IDs and preserves unrelated records. Dashboard, roadmap and reader continue to use the same store and progress calculation.
- The reader's completion button uses an explicit completion action, not a toggle that might undo a successful double-click. Reload displays a busy state, uses `cache: no-store`, and cannot replace a pending write. Successful reload clears stale errors; failures preserve the last saved snapshot and present actionable feedback. Expired sessions disable editing and offer sign-in.
- Successful login clears the prior account's cache before displaying the new account. Logout already clears it.

## Stable identifiers

All 17 canonical chapters now declare `<!-- lesson-id:wN-section-... -->` metadata beside reading sections. The values are exactly the IDs previously generated by the loader, so no existing record needs renaming or migration. Keep these comments unchanged when editing headings; the loader now requires unique metadata and retains a stable persistence ID even when the current anchor/title changes. The metadata is not displayed as lesson text. Existing concept-checkpoint and legacy mastery IDs are retained.

## Production observations and limits

Non-mutating checks against the deployed services confirmed:

- Render `/api/health`: HTTP 200 and `database: connected`.
- PATCH preflight for the progress endpoint: HTTP 204 with the exact production Vercel origin, credential support and CSRF/content-type headers allowed.
- Unauthenticated `/api/progress`: HTTP 401, as required.
- The deployed Vercel JavaScript bundle contains `https://dsa-study-buddy.onrender.com` as its API origin. It is not calling a Vercel serverless filesystem for persistence.

The database configured locally has migrations 001–006 applied. Migration 007 from the curriculum split is absent there. It is required for stable module ID 17 (Arrays), but is **not** the cause of the Complexity module's reproduced 42883 error. Without Render environment/dashboard access, the local connection must not be assumed to be identical to Render's configured database.

No production account was created or modified. An authenticated production completion/refresh/logout/login flow has not been verified, and this local patch has not been deployed. Render request logs were not available; the SQL root cause was reproduced directly instead.

## Verification and deployment

Run `npm test`, `npm --prefix frontend test`, and `npm run build`. The repository has no configured lint command; syntax tests and formatting checks cover the changed JavaScript.

From the backend directory, `node src/check-learning-integration.js` uses a random schema in one transaction. It reproduces the old error, exercises the real fixed service, checks completion/reopening, duplicate preservation, stale starts, activity-failure rollback and account isolation, and rolls all fixtures back. It never edits actual account records or marks migration 007 as applied in production.

Before release:

1. Back up the intended database and confirm which `DATABASE_URL` Render uses. Apply existing migrations with `npm run migrate` if 007 remains pending. This fix adds no new SQL migration or environment variable.
2. Deploy backend and frontend from the same commit, including annotated Markdown chapters. Keep the existing HTTPS API base URL, cookie and CORS configuration.
3. In an authorised test account, complete a section, inspect the PATCH JSON snapshot, refresh, navigate to the dashboard/roadmap, log out, log back in, and confirm the same completion persists.
4. Simulate a failed request, restore connectivity, and use Reload saved progress. Confirm a pending save is not discarded and that a second account cannot see the first account's records.
5. If a failure remains, inspect the server's `checkpoint-save`/`checkpoint-load` diagnostic code. Do not paste connection strings, cookies, passwords or CSRF values into bug reports.

Key changed areas: the progress service and routes, Markdown identity loader and chapter metadata, API error classification, shared progress store, lesson/reload controls, login cache clearing, and backend/frontend regression tests.

- All 18 root test files passed, including backend/shared syntax and stable-ID rename checks.
- All 27 frontend tests passed, including completion idempotency, authoritative snapshots, reload busy/error states, expired sessions, stale responses and account-cache isolation.
- The production Vite build and prerender passed; `git diff --check` passed.

Authenticated production saving remains unverified until deployment and an authorised account test. No new migration or backend environment variable was introduced by this patch.
